# SWARM — 3D Simulation Studio Performance (Mission 007)

Everything below was measured with the harness in `tests/perf/studio-3d.perf.mjs`. Nothing is estimated unless it says so. Raw results: [`perf/studio-3d-before.json`](perf/studio-3d-before.json) and [`perf/studio-3d-after.json`](perf/studio-3d-after.json).

## Environment

| | |
|---|---|
| Machine | Apple M5, 10 cores, macOS (Darwin 27.2, arm64) |
| Browser | Google Chrome 158, headless, via Playwright 1.65 |
| GPU path | ANGLE Metal renderer (hardware WebGL 2, not software) |
| Viewport | 1440 × 900 at device pixel ratio 1 |
| Build | `next build` + `next start` (production) |
| App quality tier | `high` (shadows on) — chosen by the app's own device detection |

The browser is vsync-locked at 60 Hz in both headless and headed mode on this machine (`--disable-gpu-vsync` / `--disable-frame-rate-limit` had no effect), so **FPS saturates at 60 in every case** and cannot separate them. The harness therefore also measures the **main-thread cost of each rendered frame**, which shows where the work goes.

## Method

`npm run build && npm run perf:3d` (set `PERF_OUT=file.json` to save results). Preferences are reset to their defaults first. The harness then runs these steps:

1. **Fleet sizes.** For each case it loads the scenario, presses Play, warms up for 1.5 s, then samples for 5 s:
   - `requestAnimationFrame` intervals: FPS, mean, p95 and max frame time.
   - Main-thread frame cost: the time between R3F's `addEffect` and `addAfterEffect` around every rendered frame. That covers all `useFrame` work plus scene submission to WebGL, but not GPU execution.
   - Renderer counters read from the 3D view's stats readout: `gl.info.render.calls` / `triangles` for one frame, shadow pass included, plus live geometries, textures and shader programs.
   - JS heap after two forced GCs (`--expose-gc`).
2. **Initial load.** Navigation start to the first rendered 3D frame, on a cold page.
3. **Selection.** Clicks robots in the 32-robot view and measures from `pointerdown` until the robot inspector is in the DOM (MutationObserver). It then double-clicks to follow a robot and samples frames for 3 s while the simulation runs.
4. **2D ⇄ 3D.** Ten switches, timing each 2D → 3D switch to the first 3D frame. Resources are read before and after.
5. **Scenario loads.** Three cycles of medium → dense → large → small (12 loads), with resources read before and after on the same scenario.

| Case | Scenario | Robots | Layout |
|---|---|---|---|
| Small | Standard warehouse | 5 | 28 × 18 |
| Medium | Stress test · 15 robots (synthetic) | 15 | 32 × 21 |
| Large | Stress test · 32 robots (synthetic) | 32 | 40 × 27 |
| High density | High-density warehouse (narrow aisles, heavy feed) | 8 | 26 × 16 |

The stress-test layouts are generated by `src/engine/scenarios/stress.ts`, the same generator the engine benchmark (`npm run bench`) uses. They are labelled as synthetic in the scenario selector.

## Results

"Before" is the Mission 006 renderer with only the measurement hooks added. "After" is Mission 007. The before numbers come from one run; the after column for frame cost gives the range over two runs. Frame-cost means move by roughly ±0.5 ms between runs because of GC and timer noise, so treat small differences as noise. Draw calls, triangles and resource counts are deterministic.

### Per fleet size

| Case | Draw calls | Triangles / frame | Live geometries | Frame CPU mean | FPS (vsync-capped) | Heap |
|---|---|---|---|---|---|---|
| Small (5) | 180 → **88** | 79.8k → 77.1k | 55 → 32 | 1.92 → 1.14–1.35 ms | 60 → 60 | 18.1 → 18.1 MB |
| Medium (15) | 425 → **205** | 125.3k → 116.4k | 57 → 34 | 2.49 → 1.32–2.28 ms | 60 → 60 | 20.3 → 20.4 MB |

Neither build shows resource growth across view switches or scenario loads: geometry and texture counts stay flat. The heap differs by about 1 MB, which is within GC variation for a single run.

A note on the selection numbers. An intermediate Mission 007 build measured **39 ms**, because the inspector waited for an exit animation before mounting the new entity. The harness caught this, and the transition was changed to enter-only before the final run.

## What changed, and why

Profiling showed draw calls growing at roughly 22 per robot (712 at 32 robots), with every robot also raycast mesh by mesh on each pointer move. These were the targets:

| Change | Effect |
|---|---|
| Shared robot model: identical-material parts merged (eye pair, sensor pair, tyre and hub pairs per axle, status strip + beacon, tote + lid) | Fewer meshes per robot at full detail. Same silhouette and face. Wheel spin is now visible (spoked hubs). |
| Distance LOD for robots in the Studio: beyond 15 units from the camera (shown again under 13) the bezel, eyes, sensors, seam, hub caps and LiDAR window are hidden | Distant robots cost about 10 draw calls instead of about 22. The Fleet portraits always render full detail. |
| One invisible hit box per robot, and one instanced pick volume for all rack and obstacle cells | R3F raycasts every interactive object recursively on each pointer move. A robot used to mean about 22 mesh raycasts; now it is 1. Visible rack geometry is never raycast. |
| Stations instanced per part (4 draw calls in total); closures instanced (3 draw calls in total, previously 4 meshes per closed cell, each with its own geometry and material) | Constant cost however many stations or closed cells there are. |
| Adaptive DPR never rises above the display's own pixel ratio | Before, `PerformanceMonitor` could raise DPR to 1.5–1.75 on a 1× display, wasting fill rate. Seen in the baseline's readout. |
| Floor texture limited to 4096 px on its longest side, with markings scaled to match | Very large layouts no longer create oversized textures. Layouts up to 85 cells wide keep the original density. |
| Ring materials disposed when robots unmount | Fixes a per-robot material leak on scenario switch. |

Deliberately not added: post-processing, SSAO and extra shadow-casting lights. Frame cost was already low on this machine, and they would raise GPU cost on weaker hardware for little gain in readability.

## Limits of these numbers

- One machine, one browser, one GPU. Integrated or older GPUs will show different absolute numbers. Draw calls and triangle counts carry over between machines; frame times do not.
- GPU execution time was not measured: `EXT_disjoint_timer_query` is not available here. Frame CPU cost covers JS work and WebGL submission only.
- FPS is vsync-capped, so headroom above 60 FPS is not visible in these results.
- Each "before" figure is a single run.
